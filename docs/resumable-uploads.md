# Resumable dataset uploads

A durable upload session reserves the declared file size against its project's storage quota before accepting bytes. Each chunk has an explicit offset and SHA-256, and is recorded only after its content-addressed blob is stored. Repeating the same chunk is safe; conflicting content or out-of-order offsets are rejected. Completion verifies the assembled size and optional full-file hash, then commits the dataset-file reference and releases the reservation in the same transaction. Draft versions cannot be sealed with open transfers.

The web uploader uses bounded chunks, checks their hashes and shows progress. Selecting the same file again finds its existing session and verifies/replays recorded chunks before completing. It never loads the entire file into browser memory. CLI/SDK clients also provide the full-file hash and resume directly from the acknowledged byte offset, avoiding retransmission of confirmed chunks.

For an explicit recovery path, run `strata upload-start VERSION_ID FILE`; retain the returned upload ID. Transfer with `strata upload-file VERSION_ID FILE --upload-id UPLOAD_ID`. On interruption, run the same command again. Inspect sessions with `strata uploads`, or release a reservation with `strata cancel-upload UPLOAD_ID`. The SDK equivalent is `Client.upload_resumable(version_id, Path(file), upload_id=upload_id)`. An existing draft version is required; use the dataset/version API or web to create one.

Defaults are 8 MiB chunks, 24-hour session expiry, 1,000 simultaneous active transfers and the deployment's existing dataset-file size limit. Configure `STRATA_UPLOAD_CHUNK_BYTES`, `STRATA_UPLOAD_LIFETIME_SECONDS` and `STRATA_UPLOAD_MAX_ACTIVE`. Expired/cancelled sessions cannot accept new chunks; expired reservations do not consume admission quota. A completed session returns the same file when completion is retried. Zero-byte files are supported.

The selected filesystem/S3 backend stores chunk blobs as well as final files. PostgreSQL stores upload state, offsets, hashes, expiry and ownership. Backups include referenced chunks so unfinished transfers survive restore. API replicas require the same database and durable object backend (or shared filesystem). S3 caches can be independent. Closing the browser or restarting an API does not erase acknowledged progress.

Chunk blobs and session history remain after cancellation/expiry/completion until a retention policy removes their references and then safely reclaims unreferenced bytes. A reservation measures logical final-file storage, not transient physical duplication during assembly. Administrators must provide sufficient staging space; storage admission still checks local free space. Resumable sessions do not establish an unlimited file size or automatic cache eviction.

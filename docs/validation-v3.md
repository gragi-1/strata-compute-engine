The isolated load recorded 24.59-second median and 43.26-second p95 end-to-end latency, about 0.304 jobs/second. These include queueing, bounded helper/container startup, computation, download and polling. No other Docker builds, scans or integration workloads overlapped this final run. These small hash-producing workloads do not establish isolated kernel performance, maximum throughput, large-input/large-output performance, GPU utilization, a multi-host benchmark or an availability SLO. One hour does not establish day-long endurance.

The environment was one Windows computer with Python 3.13.5, PostgreSQL 17, Linux Docker Desktop and an RTX 3050 Laptop GPU. Actual CUDA artifacts were checked through both agents and unreserved GPU access was denied. Logical worker, coordinator, PostgreSQL and etcd nodes shared that physical host.

## Failure behavior and corrections

Two coordinator replicas used shared actual S3 bytes and verified RPC TLS. Killing one during execution preserved one attempt and delivered output through both replicas after recovery. First successful survivor API responses were observed after 0.21 seconds for the Python path and 3.42 seconds for C++. PostgreSQL primary recovery took 24.48 seconds; write authority was withdrawn 8.68 seconds after DCS quorum loss. Nodes rejoined and DCS used mutual TLS. These are individual one-host observations, not physical failure-domain or client-wide recovery guarantees.

Both agents hit actual kernel output byte/inode limits with tmpfs `noswap`, retained output after workload exit, failed explicitly after keeper loss/oversized transfer and released persisted helper charges. Container cleanup, caches, live logs, experiment replay, dynamic fan-out/join, GPU reservations, bounded Docker host pools, abrupt provisioning-controller exit and foreign-container preservation were exercised.

Earlier sustained runs exposed unseen batch leases during serial startup and ambiguous Docker start replies. Corrected agents discover committed assignments during heartbeats, renew received batches and reconcile an owned keeper/workload's lost start reply without repeating that mutation. Cancellation and watchdog outcomes remain authoritative. Temporary coordinator disconnects during startup preserve only an unexpired lease; they never extend it without an authenticated renewal. Explicit daemon/authentication/session rejections still fail or fence execution.

Concurrent load and integration also encountered bounded Docker startup/readiness failures. Those failed records remain available. The keeper now uses Linux `statvfs` directly instead of loading unused compression modules through `shutil`, retaining its 0.01 CPU, 32 MiB memory and ten-second readiness bounds. The final integration and sustained-load runs were isolated from each other. A paused host is a separate failure: Windows event logs confirmed actual suspension/resumption during another interrupted run. Its expired-lease results were retained. The final run used a bounded temporary automatic-sleep inhibitor, released afterward; no power-plan change was made. See [the reliability guide](reliability-validation.md) and [failure semantics](fault-tolerance.md).
